# bili-retention

留存曲线是平台给你的最诚实的反馈。几乎没人认真读它。

```bash
bili retention retention.csv --transcript transcript.srt --danmaku danmaku.xml
bili retention retention.csv --duration 600       # 横轴是进度百分比时，给出时长
```

工具是这个仓库的 `bili` 命令（Go 写的，零依赖，只读本地文件，不登录、不调 B站接口）。没装的话：

```bash
go install github.com/venciallee/bilibili-agent-skill/cmd/bili@latest
```

装不了 Go 时，按下面的规则手工检查，并在输出里写明“这次没有跑工具”。

## 拿到曲线

在创作中心的数据中心 / 稿件分析里找到这个稿件的观众留存（播放完成率）曲线。入口和叫法会随版本变，**以用户看到的为准**，不要替他编菜单路径。

不一定有导出按钮。没有就请用户截图发过来，你逐点读出 15 到 20 个点，写成两列 CSV：`时间（秒或 M:SS）, 留存百分比`。告诉用户这是估读，断崖位置有一个采样间隔的误差。

## 三种不同的问题

- **开头流失**：前 30 秒（以及前 5 秒）丢了多少。25% 以内算健康是经验阈值，不是 B站官方基准。这永远是第一个要修的，而且永远是前 15 秒的**稿子**，不是剪辑。
- **断崖**：单点陡降，是某个**时刻**：没有过渡的转场、口播广告、太长的铺垫、一段讲懵了的解释。相邻的陡降会合并成一段。加 `--transcript` 打印那里在说什么，加 `--danmaku` 打印那里观众在打什么——断崖前一片“？？？”是讲懵了，断崖前有“空降”是观众在跳。这才让报告能动手改，而不只是有意思。
- **滑坡**：中段稳定地往下掉。平稳的滑坡是节奏问题，修法是剪，不是重写。

## 交回什么

指出**最大的那一个漏点**，配一个改法。不是五条清单。用户问了再给其余的。如果开头流失健康、滑坡平缓，就直说视频本身没问题，问题在包装——把用户送去 `/bili-package`。

## 闸门

这里什么都不会发布。skill 只负责写，投稿由你来点。每次输出都以一个可以直接复制的块结尾，最后一句永远是：**就这么发，还是改？**
